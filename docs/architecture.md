# Архитектура десктопного приложения poe-manager

> Живой документ: здесь записываются принятые решения по десктопу.
> Десктоп — **отдельный репозиторий**. Соседние: `backend` (BFF и сборщик данных), `extension` (расширение браузера), `docs` (общие документы: общая архитектура, источники данных, схема предметов, ТЗ на дизайн).

### Почему Tauri, а не Electron

- Меньше памяти (приложение работает рядом с игрой), установщик ~10 МБ вместо ~90 МБ, быстрее запуск.
- Работа с WinAPI (хуки, окна, `SendInput`) и мост Native Messaging естественно ложатся на Rust.
- Интерфейс остаётся веб-технологией: дизайн-систему можно делить с расширением.
- Парсер на Rust можно собрать в WASM и использовать в расширении.

**Чем платим:** готового аналога `electron-overlay-window` нет, оверлей пишем сами. Это главный риск, его проверяет прототип. Если прототип не пройдёт — запасной вариант Electron.

**Чего не ждём:** заметного ускорения отклика. Дольше всего в цепочке «клавиша → панель» ждём, пока игра положит текст в буфер обмена (десятки мс), а это от нашего языка не зависит.

## Процессы и окна

```
┌─ Rust-ядро (src-tauri) ──────────────────────────────────────┐
│ жизненный цикл, трей, single-instance                        │
│ горячие клавиши → Ctrl+Alt+C → буфер обмена → текст предмета │
│ поиск окна PoE и слежение за ним (позиция, фокус)            │
│ item-parser: текст → структура предмета                      │
│ синхронизация с BFF, кэш в %APPDATA%, настройки, логи        │
│ протокол для иконок из кэша                                  │
│ позже: мост Native Messaging, обновления, Client.txt         │
└───────────────┬──────────────────────────────────────────────┘
                │ Tauri commands + events (serde, JSON)
     ┌──────────┴──────────┐
┌────▼────────────┐  ┌─────▼──────────────────────┐
│ Главное окно    │  │ Оверлей                    │
│ React: оболочка │  │ React: прозрачное окно     │
│ и модули        │  │ поверх игры, виджеты       │
└─────────────────┘  └────────────────────────────┘
```

- **Текущий предмет один на всё приложение.** Ядро разбирает предмет и рассылает событие в оба окна.
- **Интерфейс не содержит игровой логики.** Он показывает то, что прислало ядро, и отправляет команды.
- **Права интерфейса ограничены** через capabilities Tauri: окну доступны только явно разрешённые команды.

## Структура репозитория

```
desktop-application/
├─ src-tauri/                 приложение (Rust)
│  ├─ src/
│  │  ├─ main.rs, lib.rs      запуск, окна, трей
│  │  ├─ hotkey.rs            горячая клавиша
│  │  ├─ capture.rs           Ctrl+Alt+C → буфер обмена → текст
│  │  ├─ game.rs              слежение за окном PoE (поток раз в 700 мс → событие game-status)
│  │  └─ overlay.rs           прозрачное окно поверх игры
│  ├─ capabilities/
│  └─ tauri.conf.json
├─ crates/
│  ├─ item-parser/            разбор предмета: чистый Rust, тесты через cargo test
│  ├─ game-window/            поиск окна PoE через WinAPI: режим, фокус, права; пример fake_poe
│  ├─ craft-engine/           движок крафта кластеров: вероятности, методы, план; примеры evaluate, weights
│  └─ pob-parser/             код экспорта Path of Building → сборка (предметы, наборы, камни, деревья); пример dump
├─ ui/                        React + Vite: главное окно и оверлей
│  └─ src/
│     ├─ design-system/       токены, компоненты, оболочка (см. design-system.md)
│     ├─ app/                 состояние, реестр модулей, окно Tauri
│     ├─ modules/             страницы модулей
│     └─ showcase/            витрина компонентов (только dev)
├─ scripts/                   генератор токенов, проверка токенов, скриншоты
├─ docs/
└─ Cargo.toml                 workspace
```

Основные библиотеки Rust:
- `windows` — WinAPI от Microsoft: окна, `SendInput`, `SetWinEventHook`;
- `tauri-plugin-global-shortcut` — горячие клавиши (для прототипа); если не хватит — низкоуровневый хук `WH_KEYBOARD_LL`;
- `serde` — обмен данными с интерфейсом.

## Прототип

Каждый шаг даёт проверяемый результат.

| Шаг | Что делаем | Готово, когда |
|---|---|---|
| 1 | Пустое приложение Tauri + React | `pnpm tauri dev` открывает окно, `pnpm tauri build` даёт exe, и он запускается |
| 2 | Поиск окна игры ✅ | В главном окне статус «Игра найдена / не найдена» меняется при запуске и закрытии PoE |
| 3 | Оверлей | Прозрачное окно поверх PoE (Windowed Fullscreen), клики проходят сквозь него, окно следует за игрой и прячется, когда игра теряет фокус |
| 4 | Захват предмета | Клавиша в игре → в оверлее сырой текст предмета, прежнее содержимое буфера обмена восстановлено |
| 5 | Первый парсер | Редкость, название, база, моды с тирами и диапазонами на наборе примеров; тесты проходят |

Шаги 3 и 4 решают, остаёмся ли мы на Tauri.

### Связь с сервером

- Ядро (`src-tauri/src/server.rs`) в своём потоке запрашивает `GET {адрес}/v1/health` (таймаут 3 с): пока связь есть — раз в 15 с, когда нет — раз в 5 с. Результат — событие `server-status` и команда `server_status`. Сервер считается доступным при любом ответе 2xx; поле `version` из JSON-ответа необязательно.
- Адрес, по убыванию приоритета: задан на странице «Режим разработки» (действует, только пока в Настройках включён режим разработчика; сохраняется между запусками, команда `server_set_url`) → `API_URL` в окружении при запуске (в отладочной сборке читаются и `.env.local` / `.env`) → `API_URL`, заданный при сборке.
- Интерфейс: статус «Сервер» в строке статусов (задержка, версия, причина ошибки, «Проверить сейчас»), карточка «Сервер» на странице «Режим разработки», настоящий шаг «Подключение к API» на экране запуска. Без связи приложение продолжает работать.
- Пока бэкенда нет: `pnpm mock:api` поднимает тестовый сервер на `http://localhost:8787`. Остановите его — через несколько секунд статус станет «Нет связи с сервером».
- Запрос делает ядро, а не WebView: нет CORS, и вся связь с BFF в одном месте (принцип BFF из общей архитектуры).

### Связь с расширением (Native Messaging, этап 1)

Протокол и решения — в общих документах: `docs/extension-bridge.md`.

- **Крейт `crates/browser-bridge`** (без Tauri): кадры «4 байта длины + JSON», протокол, именованный канал
  `\\.\pipe\poe-manager-bridge-<пользователь>` (доступ только текущему пользователю), сервер `Hub`, мост `relay`, регистрация.
- **Режим «мост»:** Chrome запускает `poe-manager.exe chrome-extension://<id>/`. `main.rs` видит аргумент и до запуска Tauri
  пересылает кадры между stdio и каналом запущенного приложения. Приложения нет — сообщает расширению `app-status: false`
  и ждёт; само приложение не запускает. Лог: `%LOCALAPPDATA%\com.poemanager.desktop\logs\bridge.log`.
- **При запуске приложения** (`src-tauri/src/extension.rs`): манифест хоста + ключ `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.poemanager.bridge`
  (путь к exe каждый раз сверяется), сервер канала, событие `extension-status` и команда `extension_status`.
  Ключ удаляет деинсталлятор (`src-tauri/windows/hooks.nsh`).
- **Интерфейс:** статус «Расширение» в строке статусов (`ui/src/app/extension.tsx`): «подключено · Chrome · версия»,
  нейтральное «не подключено», предупреждение — только если сломан сам мост (не удалась регистрация, канал занят вторым экземпляром).
  Симуляция «Расширение подключено» на странице «Режим разработки» осталась.
- **ID расширения** — `abnbkbopbfhbfbinmeihjniikcamacol` (поле `key` в манифесте расширения). ID из Chrome Web Store добавляется
  переменной сборки `POE_MANAGER_EXTENSION_IDS`.
- **Проверка:** `cargo test -p browser-bridge`; `node scripts/bridge-smoke.mjs` — exe в режиме моста «как из Chrome»
  (с запущенным приложением или примером `cargo run -p browser-bridge --example fake_app`).

### Discord Rich Presence

План и решения — в общих документах: `docs/discord-rich-presence.md`.

- **Крейт `crates/discord-presence`** (без Tauri): кадры IPC Discord (`opcode + длина + JSON`), поиск канала `\\.\pipe\discord-ipc-0..9`,
  сессия с переподключением раз в 15 с (`session::run` + `Handle`), активность, ключ запуска `HKCU\Software\Classes\discord-<client_id>`.
  Прототип без приложения: `cargo run -p discord-presence --example spike`.
- **`client_id`** — `DISCORD_CLIENT_ID`: окружение при запуске (в отладочной сборке и `.env.local` / `.env`) → значение при сборке.
  Не задан — Discord-часть выключена (статус `noClientId`).
- **При запуске приложения** (`src-tauri/src/discord.rs`): ключ запуска по приглашению → этот exe, сессия в фоне.
  Статус собирается по игре: PoE1 запущен — «Торгует в Path of Exile» с таймером, группа и `join secret` `pm1:open`; нет — статус снят.
  `game.rs` сообщает об изменении игры (`discord::on_game_status`). Событие `discord-status` (с журналом последних 100 кадров обмена),
  `discord-join` при нажатии «Присоединиться»; команды `discord_status`, `discord_configure`, `discord_reconnect`, `discord_clear_log`.
- **Интерфейс** (`ui/src/app/discord.tsx`): переключатель «Показывать статус в Discord» (`discordPresence` в `store.ts`, по умолчанию
  включён). Страница «Режим разработки» → раздел «Discord»: связь, переопределения (когда показывать, тип активности, размер группы —
  сбрасываются при выключении режима разработчика), журнал обмена с Discord и состояние в «Сырых данных ядра».
- **Ещё не сделано:** переключатель в Настройках, единственный экземпляр приложения (второй запуск от Discord), удаление ключа деинсталлятором.

### Учёт Ancient Orb (MVP)

План и полная версия — в общих документах: `docs/ancient-orb-tracker.md` (раздел 2 — MVP).

- **Модуль `ui/src/modules/ancient-orb/`**, вкладка «Ancient Orb» в группе «Крафт». Переносит сайт «Ancient Orb казино»: сколько сфер ушло в попытку и за сколько выпала цель.
- **Модель** (`model.ts`): трекеры (название, цели — свободный текст, ожидаемое среднее на находку, текущая лига — текстовая метка) и журнал событий `spend` / `hit`. Попытки и итоги вычисляются из журнала: удаление находки не теряет сферы — они уходят в следующую попытку.
- **Хранение** (`store.ts`): zustand `persist`, ключ `poe-manager.ancient-orb`. Это временное отступление от «данные пользователя — `user.db`»: когда база появится, ключ один раз переносится в неё. У `pnpm tauri dev` и у собранного приложения хранилища WebView разные; очистка данных WebView стирает учёт — поэтому есть «Резервная копия» (JSON в буфер обмена и обратно).
- **Импорт с сайта**: JSON из `localStorage['ancient-orb-tracker-v1']`; id записей строятся от id сайта, повторный импорт ничего не задваивает.
- **Картинки** целей Headhunter / Mageblood и сферы — из сайта (`assets/`), по совпадению имени цели; остальным — значок по умолчанию.
- **Скриншоты:** `?demo=ancient` (только dev-сервер) заменяет учёт демо-данными; кадры `ancient-*` в `scripts/screenshots.ps1`.

### RegEx карт

Разбор сайта «Атлас — конструктор RegEx» и план — в общих документах: `docs/map-regex.md` (раздел 2), данные бэкенда — `docs/map-mods-backend.md`.

Вкладка «RegEx карт» в группе «Крафт» собирает строку для поиска во вкладке сундука: какие моды карт исключить или требовать, пороги наград и качества, состояние, редкость, типы карт.

- **Данные** — файл `map-search.json` набора данных: 125 семейств модов карт (ключ `map:<slug>[:nightmare]`, строки EN/RU, токен поиска EN/RU и пересечения) и 24 свойства карты. Ядро (`src-tauri/src/dataset/`) разбирает его вместе с набором, команда `catalog_map_search`: `null` — в наборе нет файла (старый набор), ошибка — формат новее приложения. Файл необязательный: если он не разобран, набор всё равно ставится — справочник и цены не зависят от вкладки. Счётчики `mapMods` / `mapProperties` в статусе набора берутся из самого файла.
- **Модуль `ui/src/modules/map-regex/`:**
  - `regex.ts` — чистые функции без импортов во время выполнения (запускаются и в Node): `buildExpression` (правила блоков, порогов и их порядок — как на сайте; сверено с кодом сайта на 20 000 случайных наборов) и `parseExpression` (строка → набор: наши токены, затем регулярка против текста игры — узнаются и строки poe.re).
  - `model.ts` — запись набора, нормализация, индекс данных, тексты проблем выражения, чистые правки (отметка мода, порог, признак, сбросы, применение разобранной строки, пропавшие ключи).
  - `store.ts` — наборы и вид вкладки; `useMapSearch.ts` — данные из ядра, перечитываются при смене набора данных.
  - `MapRegexPage.tsx`, `parts.tsx` (выражение, колонки модов, баннер пропавших), `options.tsx` (параметры карт), `dialogs.tsx` (имя набора, подтверждение, вставка выражения, импорт наборов), `backup.ts` (импорт с сайта, экспорт копии), `data/site-mods.json`.
- **Наборы** — синхронизируемая коллекция `mapRegexPresets` в `user.db` (проверка записи — `sync/records.rs`, те же правила, что `MapRegexPreset` на сервере). Ключи модов и свойств проверяются только по формату: мод, ушедший из игры, остаётся в наборе и показывается баннером «Больше не встречается» с кнопками «Убрать». Правка видна сразу и пишется через 400 мс. Пока наборов нет — несохранённый черновик «Мой первый набор», он записывается при первой правке (новое устройство не плодит пустых наборов). Вид вкладки (Nightmare, P/S, по типу) и активный набор — локально, zustand `persist` `poe-manager.map-regex-view`.
- **Наборы — столбиком слева** (`rail.tsx`, просьба пользователя: из выпадающего списка в шапке было непонятно, что наборов несколько): название и сводка («RU · −3 · +2 · 4 парам.»), у строки «⋯» — переименовать / удалить, внизу «Новый набор», в заголовке — импорт / экспорт. Столбик стоит рядом, если справа остаётся ≥ 880 px (четыре карточки параметров), иначе — полоса 52 px с буквами наборов, раскрывается поверх содержимого. Свернуть можно и вручную (`railCollapsed`). При наведении на набор (строку или букву) справа выезжает карточка (`preview.tsx`, Radix HoverCard): исключённые и нужные моды (до 6 на колонку), параметры карт со значениями («Item Quantity ≥ 80%», «Corrupted: Exclude»), пропавшие моды и готовое выражение набора — без переключения на него.
- **Выражение** (`ExpressionCard`): крупная строка в акцентной рамке, блоки подсвечены по смыслу (`Expression.parts`: исключить, нужные, пороги, признаки «только»/«кроме») с легендой, полоса длины (зелёная → жёлтая с 80 % → красная за 250). Предупреждения — кнопками по видам (ошибки, конфликты/пересечения модов, строка целиком, длиннее 250), по клику — подробности. Пересечение (токен мода находит и другой, обычно Nightmare-близнеца) делится на **конфликт** — другой мод отмечен в противоположной колонке, поиск сработает против выбора (действие «Снять …») — и **захват** — другой не отмечен (действие «Отметить их …»). В колонках захваченный мод — штриховая рамка со значком связи и «захвачен», в подсказке — через какой мод (`impliedChoices`).
- **Окно не прокручивается, списки модов — да:** колонки «Исключить» / «Нужные» — все 125 модов с прокруткой внутри колонки (решение пользователя 11.11.2026 вместо страниц — исключение из правила дизайн-системы «большие списки постранично»; внизу «125 модов» / «Найдено N из 125»; поиск и смена вида возвращают список к началу, отметка мода — нет); параметры карт — переключателем «Моды | Параметры карт» на месте колонок (над колонками не помещаются). В панели параметров подписи по-английски, как текст карты в игре (просьба пользователя).
- **Импорт с сайта:** сайт хранит выбор мода по номеру в своём списке из 118; `data/site-mods.json` — наши ключи в том же порядке (сопоставлено по тексту и проверено токенами сайта, 236 из 236). Текстов и токенов poe.re в репозитории нет — у poe.re нет лицензии. Экспорт — JSON всех наборов в буфер обмена, восстанавливается тем же диалогом.
- **Проверка без приложения:** вкладку можно открыть в браузере поверх Vite (`?module=map-regex&splash=0`) с подменой `window.__TAURI_INTERNALS__` — так она проверялась на 1440×900 и 1280×720.

### Движок крафта кластеров

План функции «Выгодные кластеры» — `shared/docs/cluster-crafting.md` (бэкенд готов: цели, спрос и цены с сайта торговли — `GET /v1/crafting/clusters/:league`, данные игры — `crafting.json` набора).

Крейт `crates/craft-engine` (без Tauri и сети; `serde`, `serde_json`):

- **`data`** — `crafting.json`: размеры (теги базы, пассивы), энчанты (тег), моды кластеров (веса появления и генерации в порядке игры, группы, стороны, `implicit_tags`, `adds_tags`, notable), ископаемые, ключи валюты.
- **`Pool`** — моды базы (размер, энчант, уровень предмета) с весом `появление × генерация / 100 × ископаемые`; в списках весов берётся первый тег предмета, включая добавленные выпавшими модами (`has_affliction_notable`: у малого кластера второй notable невозможен). Ископаемые — как в Craft of Exile по умолчанию: множители больше 1 по тегам мода складываются, меньше 1 — перемножаются, вес 0 запрещает мод. Моды собраны в корзины (те же группы, сторона, добавляемые теги, notable цели): тиры одного мода для цели неразличимы.
- **Точный расчёт** (`reroll_hit_probability`) — моды выпадают по одному из общего пула с учётом мест (магический 1+1, редкий самоцвет 2+2), групп и тегов; рекурсия по набору выпавших корзин с запоминанием (корзин ≤ 38 на базу). Число модов — доли Craft of Exile: магический 1 или 2 поровну, редкий самоцвет 3 (65 %) или 4 (35 %).
- **Монте-Карло** (`simulate_reroll`) — то же по отдельным модам, SplitMix64 с зерном; проверяет корзины и рекурсию.
- **Методы на базе** (`evaluate_base`): перемены; перемены + усиление; + царь; + возвышение; хаос (алхимия + хаос); ископаемые (лучший набор до 3 из 5 лучших по одиночному шансу, резонатор по числу). Многошаговые (`strategy.rs`, общий `Decider` для точного расчёта и Монте-Карло): усиление — если у предмета один мод и усиление может закончить цель (или дать notable, с которым её закончит царь); царь — если на предмете есть notable цели и добавленный мод может её закончить (сам или с возвышением); возвышение — если после царя не хватает одного мода; неудача после царя — очищение + превращение. Любой метод — повтор независимых попыток, поэтому попытки геометрические: шанс попытки, попытки (среднее, p50, p90), стоимость без базы; метод, не отличающийся от более простого (одиночная цель: царь не нужен), не выводится; без цен — пропуск.
- **Harvest (H2)** — перековка редкого предмета «…включая свойство тега» (`crafting.json.harvest`, выгружается бэкендом из файлов игры): первый мод выпадает только из модов с тегом (теги мода — `implicit_tags`), остальные — как при хаосе, число модов — как у редкого самоцвета, считая первый (так же у Craft of Exile); `harvest_hit_probability`, Монте-Карло `simulate_harvest`. Способ `harvest`: алхимия (её собственный шанс не учитывается), затем перековки; пробуются теги notable цели, цена попытки — жизненная сила × цена единицы из прайса; лучший крафт по стоимости. Перековки «более / менее вероятно» не считаются: зависят от прежнего предмета. Allflame: Harvest — лучший способ у 20 из 259 целей; расчёт списка 3,2 с.
- **План цели** (`plan_target`): база = энчант + уровень + цена (их даёт приложение); для каждой базы — все методы, ископаемые — для трёх самых дешёвых баз; лучший план каждого вида по наименьшим вложениям (база + стоимость крафта), прибыль и ROI от цены продажи.
- **Проверка:**
  - `--example evaluate -- <crafting.json> [прогонов]`: 10 целей Allflame, точный расчёт против Монте-Карло на 200 000 попыток — все пять методов (перемены, + усиление, + царь, + возвышение, хаос) и ископаемые в пределах статистики (максимум 2,8 σ на 50 сравнениях, 11.11.2026); планы 10 целей — 0,7 с без Монте-Карло (15–130 мс на цель), для ~300 целей ядру нужны фон и потоки (K1).
  - `--example weights -- <crafting.json> <размер> <энчант> [уровень]` — веса модов пустой базы. Сверено с таблицей весов Craft of Exile на 6 базах (large: кинжалы/когти, стихийный урон; medium: хаос со временем, вестники; small: блок чар, броня): суммы префиксов и суффиксов и веса notable совпали точно. Вероятности самого калькулятора CoE без интерфейса не получить; число модов и правило ископаемых взяты из их кода.

### «Выгодные кластеры» в ядре (K1)

- **Данные игры** — `crafting.json` набора: необязательный файл, как `map-search.json`; `Catalog.crafting` — готовый `craft_engine::Engine` (`None` — файла нет, старый набор; `Err` — не прочитан).
- **Цели** (`clusters.rs`, поток `clusters`) — `GET /v1/crafting/clusters/:league` с ETag и кэшем `clusters\<лига>.json` + `.etag`; лига — та же, что у цен (`PricesService::league`); раз в 10 минут, после ошибки — раз в минуту, сразу — `clusters_refresh`. Поток просыпается по событиям `prices-status` и `dataset-updated` и пересчитывает, когда изменилась версия «ответ сервера | цены лиги (число ключей, самая свежая) | набор данных»; результат, посчитанный для старой лиги или старого ответа, отбрасывается.
- **Расчёт** (`cluster_plans.rs`, без Tauri, `MarketData` — прайс и справочник): цены валюты, резонаторов и ископаемых — сводные цены прайса (`variantKey = ''`); базы — варианты базы размера `enchant=…;ilvl=…;passives=…` (текст энчанта сопоставляется со строками `crafting.json` в любом порядке, через перевод строки или «, »), нужные пассивы, уровень не ниже `minIlvl`; у одного энчанта остаются только базы дешевле всех баз ниже уровнем (база выше уровнем добавляет моды в пул и дороже — хуже). `plan_target` по каждой цели (ископаемые — для двух самых дешёвых баз), цели делятся между потоками (ядра − 1, до 8). Цена продажи — котировка сервера со статусом `OK`.
- **Команды:** `clusters_status` (событие `clusters-status`: лига, `tracked`, снимок спроса, целей / с планом / прибыльных, время расчёта, ошибки сети и движка), `clusters_list` (строки: цель, имена notable en/ru, спрос, котировка, лучший план, `issue`: `unreachable` / `noBasePrice` / `noCurrencyPrice` / `notQuoted` / `noMarket`), `cluster_detail(key)` (все методы и подходящие энчанты), `clusters_refresh`. Типы — ts-rs (`ClusterRow`, `CraftPlan`, `ClustersStatus`…).
- **Проверка без приложения** — `cargo run --release -p poe-manager --example clusters_offline -- <crafting.json> <clusters.json> <prices.json>` на снимках ответов сервера (11.11.2026, Allflame, данные :5434): 259 целей, план у всех, 2,5 с на 16 потоках; котировки были у 6 целей (ROI 85 %, 75 %, 64 %, 44 %, 0 %, −30 %).

### Вкладка «Выгодные кластеры» (K2)

`ui/src/modules/clusters/`, группа «Крафт», поиск Ctrl+K: «кластер cluster крафт craft фоссил notable прибыль roi».

- `model.ts` — чистые функции: группы по ROI лучшего плана (≥ 200 %, 100–200 %, 50–100 %, 0–50 %, убыточные — только по переключателю; без цены продажи — отдельная группа), фильтры (размер, один / пара notable, поиск notable по en/ru), сортировка (ROI, прибыль, спрос, вложения), подписи методов и причин.
- `useClusters.ts` — состояние ядра (`clusters-status`) и строки (`clusters_list` перечитывается, когда меняются `computedAt` или лига); вид вкладки (группа, фильтры, сортировка, убыточные) — zustand `persist` `poe-manager.clusters-view`.
- `ClustersPage.tsx` — страница без прокрутки: группы-сегменты с числом целей, фильтры, строки по 52 px постранично (`usePageSize`). Колонки: цель (notable по-английски — так их зовут poe.ninja и сайт торговли, русские — в подсказке; размер, пассивы, ilvl), спрос (доля и изменение за сутки), цена на рынке (p25, лоты, возраст котировки), вложения (среднее и p90, в подсказке — база + крафт), прибыль и ROI, как крафтить (метод или ископаемые, энчант, ilvl базы, шанс попытки). Баннеры: лига не отслеживается сервером, расчёт недоступен (нет `crafting.json` или цен), нет связи. Свежесть: возраст снимка poe.ninja и время расчёта в подзаголовке, возраст котировки в строке.
- `demo.ts` — `?demo=clusters` (только dev-сервер): демо-цели, карточки и валюта для скриншотов в браузере; `&dialog=card` / `&dialog=currency` открывают карточку и цены валюты; проверено на 1440×900 и 1280×720.
- **Карточка цели (K3)** — `TargetCard.tsx`, по клику (или Enter) на строке: спрос, цена на рынке (лоты, возраст, минимум), лучший способ по шагам (`methodSteps` в `model.ts`), шанс попытки и её цена, попытки и стоимость (среднее, p50, p90), сравнение всех способов (база каждого — кнопкой), энчанты, на которых выпадает цель. «Трейд» — готовые самоцветы цели, «Купить базу» — база лучшего способа, «Скопировать» — имена notable. Запросы сайта торговли строит ядро (`ClusterDetail.tradeTarget`, `CraftPlan.tradeBase`, `?q=`): цель — база, notable, пассивов не больше, мгновенный выкуп, не осквернён (как проверяет цену сервер); база — белая, энчант, ровно столько пассивов, уровень не ниже; открываются через расширение или браузер (`extension_open_trade`). Проверено на Standard: оба запроса принимаются (11.11.2026 лиги Allflame на сайте торговли уже нет).
- **Свои цены валюты** — `CurrencyDialog.tsx` (кнопка «Цены валюты»): превращение, перемены, усиление, царь, возвышение, алхимия, очищение, жизненная сила Wild / Vivid / Primal (за единицу); пустое поле — цена прайса. Хранятся в zustand `persist` `poe-manager.clusters-prices` (id предмета → chaos), ядру — `clusters_set_own_prices` при открытии вкладки и каждой правке; версия своих цен входит в версию расчёта, так что пересчёт идёт сразу. `clusters_currency` — список с ценой прайса и своей.

### Как определяется окно игры (шаг 2)

- Ищем видимые окна класса `POEWindowClass` (`EnumWindows`). PoE1 от PoE2 отличаем по заголовку: «Path of Exile 2» — вторая часть. Если запущены обе — берём PoE1; если только PoE2 — статус «не поддерживается».
- Режим: свёрнуто (`IsIconic`) → эксклюзивный полноэкранный (окно на переднем плане и `SHQueryUserNotificationState` = D3D full screen) → без рамки (нет `WS_CAPTION`, окно = монитор) → оконный.
- Права: читаем токен процесса игры. Не удалось открыть процесс — почти наверняка игра от администратора. Если игра от администратора, а мы нет — предупреждение: горячие клавиши не дойдут.
- Ядро проверяет раз в 700 мс (вызов занимает микросекунды) и шлёт событие `game-status` только при изменении; начальное состояние — команда `game_status`. Для оверлея (шаг 3) слежение за положением и фокусом перейдёт на `SetWinEventHook`.
- Проверка без игры: `cargo run -p game-window --example fake_poe [-- borderless | poe2]` открывает поддельное окно. Автотест `cargo test -p game-window` делает то же самое (ненадолго показывает маленькое окно в углу экрана).

Команды:

| Команда | Что делает |
|---|---|
| `pnpm install` | ставит JS-зависимости (один раз и после изменений `package.json`) |
| `pnpm tauri dev` | запуск в режиме разработки: интерфейс обновляется на лету, Rust пересобирается при изменениях |

Результат сборки лежит в каталоге сборки Cargo. По умолчанию это `target/` в корне репозитория, но в нашей рабочей среде он вынесен наружу (см. «Окружение разработчика»):
- `<target>/release/poe-manager.exe` — запуск без установки;
- `<target>/release/bundle/nsis/poe-manager_<версия>_x64-setup.exe` — установщик.

Где каталог сборки сейчас, показывает `cargo metadata --format-version 1 --no-deps` (поле `target_directory`).

## Что учесть

- **Права администратора.** Если PoE запущен от администратора, а приложение нет, Windows не пропустит хуки и ввод в игру. Статус и баннер уже показываются (шаг 2).
- **Режим окна игры.** Оверлей виден только в Windowed и Windowed Fullscreen, не в эксклюзивном полноэкранном.
- **Модификаторы горячей клавиши.** Пока игрок держит, например, `Alt`, наш `Ctrl+Alt+C` смешается с его нажатием. Нужно учесть зажатые клавиши.
- **Одна клавиша — одно действие.** На одно нажатие игрока отправляем в игру одно копирование. Больше ничего в игру не отправляем.
- **Буфер обмена.** Сохраняем прежнее содержимое и возвращаем его после захвата.

### Режим разработчика

Включается в самом приложении: **Настройки → «Режим разработчика»** (переключатель). Сохраняется между запусками
(`developerMode` в `ui/src/app/store.ts`), действует сразу, без перезапуска и пересборки, в любой сборке. Включает:
- бейдж **Dev** в шапке окна и пометку `· режим разработчика` у версии на экране запуска;
- группу «Разработка» в навигации: **Режим разработки** (адрес сервера, окружение, сырые данные ядра, симуляция «игра не найдена» и др., повтор экрана запуска, DevTools, сброс настроек) и **Витрина** (компоненты и эталонные экраны);
- кнопку «Режим разработки» в шапке.

Выключенный режим — приложение такое, каким его видит пользователь: страницы разработки скрыты, симуляции сброшены,
свой адрес сервера не действует (связь идёт на `API_URL`; сохранённый адрес вернётся при повторном включении).
DevTools открываются только в отладочной сборке.

Для скриншотов в браузере: `?dev=1` в адресе включает режим (`ui/src/main.tsx`, только dev-сервер Vite).

`.env.example` → `.env.local` (он в `.gitignore`) по-прежнему задаёт `API_URL=http://localhost:8787`.

### Каталог сборки вынесен из рабочей папки

**Симптом:** собранный exe сразу закрывается. В журнале Windows — ошибка `0xc0000409`, в отладочной сборке — паника `Failed to setup app: Access is denied. (os error 5)`.

**Причина:** песочница агента (DeepSeek Harness) ставит на рабочую папку `poe-manager` наследуемую метку **Low Integrity**. Её получает и exe, собранный внутри. Windows запускает его с уровнем Low, а такому процессу нельзя писать в `%LOCALAPPDATA%`, где WebView2 создаёт папку данных. Это особенность среды разработки, не приложения: установленная копия работает нормально.

**Решение:** в корне рабочей папки (вне репозитория) лежит `poe-manager/.cargo/config.toml` с `[build] target-dir = "C:/Users/shoki/.cargo-target/poe-manager"`. Cargo находит эту настройку в родительской папке, и сборка идёт туда, где файлы получают обычный уровень Medium. В самом репозитории ничего не меняется: у другого разработчика сборка останется в `target/`.
